## 二、条目格式

每条知识是一个对象，字段如下：

```js
{
  id: 'crystal:C4-2',            // ★ 必须带命名空间前缀
  kp: 'crystal:C4',              // 所属知识点
  title: 'CsCl 型为什么是 8:8 配位',
  keywords: ['CsCl', '配位数', '8配位'],   // 供检索与清单展示
  source: '[周] 结构化学基础 · 离子晶体章节',  // 教材出处，便于核对
  body: '正文……',                 // 学科事实（用自己的话写）
  misconceptions: [               // ★ 常见误解——本字段最有价值
    '把 CsCl 型称作"体心立方结构"（点阵型式应为简单立方 cP）',
  ],
}
```

### 为什么 `misconceptions` 最值得花力气

这一个字段**同时服务三个节点**：

| 节点 | 怎么用 |
|---|---|
| `explain` 讲解 | 提前点出易错处 |
| `quiz` 出题 | 直接用作干扰项的来源 |
| `grade` 诊断 | 匹配错因、给出诊断动作 |

教材里的"注意"框、思考题、常见错误提示，是提炼这个字段的最佳来源。

### 单一事实来源原则

讲解、出题、诊断**引用同一份条目内容**，不得各写一份。
否则会出现"出题数值 ≠ 讲解数值"这类教学事故。

3. 解析 MTEF v2 二进制（1872 个对象、554 KB）——本机无 MathType，需自写解析器，不推荐

## 四、总知识库 `shared/` 装什么

**判据：这条知识是否会被两个以上模块引用？**

只装真正跨模块共用的内容，避免变成什么都往里塞的杂物间。

| 类别 | 会被谁引用 |
|---|---|
| 对称性与群论基础 | crystal、symmetry |
| 量子力学基础 | orbit、crystal（成键部分） |
| 化学键理论 | crystal、orbit |
| 结构—性能关联总纲 | crystal、orbit |
| **跨模块概念映射** | 全部 |

**跨模块概念映射**是总库独有的价值。举一例：

| 概念 | orbit 讲法 | crystal 讲法 | symmetry 讲法 |
|---|---|---|---|
| 简并 | n 层内 l 不同但能量相同 | 等效点系 | 不可约表示维数 |

有了这张表，统一智能体回答"为什么 3d 有 5 个轨道"和"为什么立方晶系有 3 个轴"时
能主动串起来——**这是三个独立模块各自做不到的**。

> 三个模块的交集集中在**对称性**上，所以总库应优先建对称性部分。

## 五、★ 版权红线

**必须重写，不得摘录原文。**

| 做法 | 说明 |
|---|---|
| ✅ 重写 | 吸收事实与逻辑，用自己的语言组织 |
| ✅ 标注来源 | `source` 字段标注教材与章节（属引用，合理使用） |
| ❌ 不复制原文 | 即便标注出处，大段复制仍有风险 |
| ❌ 不收录习题原文 | 教材习题可能单独享有权利；出题时自行命题 |
| ❌ 不上传扫描页 | 不把书页图片放进应用 |

**实操判据**：如果一条目的正文能被搜索引擎匹配到教材原文，说明改写不充分，需要重写。

相关赛事淘汰红线明确包含「知识产权争议」。

## 六、加载机制

知识正文**不进系统提示**。系统提示里只放清单（id / 知识点 / 标题 / 关键词），
模型需要时调用 `loadKnowledge(id)` 才拉取正文。

这样做有两个理由：
1. 正文常驻会挤占上下文、抬高每次调用的成本
2. 清单足够模型判断"该加载哪条"
