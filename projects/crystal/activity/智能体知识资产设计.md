## 一、orbit 的现成经验（可直接继承）

orbit 是与本项目同构的原子轨道可视化工具，它的教学智能体已经完整落地，代码结构与本项目应当一致。**先看清它做对了什么，再决定 crystal 怎么改。**

### 1.1 orbit 的知识资产

| 位置 | 内容 | 规模 |
|---|---|---|
| `js/agent/knowledge.js` | 知识库加载器（56 行） | 渐进式披露机制 |
| `knowledge/entries/index.js` | 知识库正文 | 36 条，覆盖 K1–K9 |
| `js/agent/skills.js` | 技能库加载器（50 行） | 渐进式披露机制 |
| `skills/index.js` | 技能正文 | 6 个技能 |

**知识条目的字段结构**（应原样继承）：

| 字段 | 用途 |
|---|---|
| `id` | 唯一标识，如 `K3-1` |
| `kp` | 所属知识点，如 `K3` |
| `title` | 条目标题 |
| `keywords` | 检索关键词 |
| `source` | 教材出处（如 `[周] 第二章 §2.4`） |
| `body` | 正文（学科事实） |
| `misconceptions` | **常见误解列表** |

`misconceptions` 字段是设计的精髓：它把"学生通常怎么错"直接写进知识条目，**同时服务于讲解、出题、诊断三个节点**。出题时用它构造干扰项，诊断时用它匹配错因——同一份数据，三处复用。

### 1.2 orbit 的三个关键机制

**① 渐进式披露（Progressive Disclosure）**

知识正文**不进系统提示**。系统提示里只放清单（id / 知识点 / 标题 / 关键词），模型需要时调用 `loadKnowledge(id)` 才拉取正文。

这样做的理由（orbit 的注释写得很清楚）：正文常驻会挤占上下文、抬高每次调用成本；而清单足够模型判断"该加载哪条"。

**② 单一事实来源**

讲解、出题、诊断三个节点**引用同一份知识内容**。orbit 在代码注释里点名了这样做的目的：杜绝"出题数值 ≠ 讲解数值"这类教学事故。

**③ 知识与技能分层**

> 技能 = 面向**过程**的方法（怎么教），知识 = 面向**内容**的事实（教什么）。

两者分层存放，各被多个节点共享。

### 1.3 orbit 技能条目的字段结构

| 字段 | 用途 |
|---|---|
| `name` / `title` / `desc` | 名称、标题、一句话说明 |
| `when` | **触发条件**——什么时候该用这个技能 |
| `steps` | 步骤序列 |
| `phrases` | 话术模板 |
| `exit` | **退出条件**——什么时候算用完 |
| `cautions` | 注意事项（含"不要做什么"） |

`when` + `exit` + `cautions` 三个字段构成完整的方法约束：**何时进、何时出、途中有何禁忌**。这比只写步骤的做法完整得多。

### 1.4 orbit 现有 6 个技能

| 技能名 | 用途 | crystal 是否可用 |
|---|---|---|
| `feynman` | 费曼式反向讲解 | ✅ 直接继承 |
| `socratic` | 苏格拉底式追问 | ✅ 直接继承 |
| `misconception-probe` | 错因探查 | ✅ 继承，诊断动作换为晶体学动作 |
| `worked-example` | 范例精讲 | ✅ 直接继承 |
| `spaced-repetition` | 间隔复习 | ✅ 直接继承 |
| `analogy` | 类比教学 | ✅ 直接继承 |

**这 6 个都是通用教学法，不依赖学科**，可以整体平移。crystal 需要在此基础上**增加晶体学专属技能**（见 §4.3）。

### 1.5 ★ 发现：`_nodePrompt` 是已定义但未使用的钩子

orbit 的 `js/agent/agent-core.js` 中有两处：

```
第 126 行：const node = window.AgentCore._nodePrompt || '';
第 339 行：_nodePrompt: '',
```

系统提示的组装方式是 `[角色契约, 知识清单, 技能清单, 节点提示].join()`。**`_nodePrompt` 被预留为"当前决策节点的专属提示"接口，但 orbit 里从未给它赋过值**——目前是空字符串，等于占位符。

这正是本项目要做的事：**把 `_nodePrompt` 从占位符变成真正的节点约束层**。见 §3。

## 二、三层知识资产架构

### 2.1 分层

```
┌─────────────────────────────────────────────────────────────┐
│  L0  总知识库  shared                                        │
│      跨模块共用的学科事实与概念映射                            │
│      例：对称性与群论基础、量子力学基础、化学键理论总纲          │
├─────────────────────────────────────────────────────────────┤
│  L1  模块知识库                                              │
│      ├─ crystal/   晶体结构（点阵、堆积、空隙、空间群…）        │
│      ├─ orbit/     原子轨道（波函数、量子数、节面、相位…）      │
│      └─ symmetry/  分子对称性（点群、对称操作、特征标表…）      │
├─────────────────────────────────────────────────────────────┤
│  L2  决策节点约束  nodes                                     │
│      每个决策节点的角色、工具白名单、输出契约、硬性禁令          │
├─────────────────────────────────────────────────────────────┤
│  L3  技能库  skills                                          │
│      通用教学法（6 个，三模块共享） + 模块专属教学法            │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 命名空间方案（为将来合并而设计）

**问题**：orbit 的知识点编号是 `K1`–`K9`，本项目的《参赛执行清单》第五章也用 `K1`–`K8` 表示晶体结构的 8 个知识点。**两套 K 编号含义完全不同**，直接合并必然冲突。

**方案**：id 采用 `命名空间:局部编号` 形式。

| 层 | id 写法 | 示例 |
|---|---|---|
| 总库 | `shared:<编号>` | `shared:S1-2`（对称操作的基本类型） |
| 晶体模块 | `crystal:<编号>` | `crystal:C4-1`（NaCl 的 6:6 配位） |
| 轨道模块 | `orbit:<编号>` | `orbit:K3-1`（R 与 D 的区别） |
| 对称模块 | `symmetry:<编号>` | `symmetry:P2-3`（C₂ᵥ 点群） |

**需要同步修改**：《参赛执行清单》里的 `K1`–`K8` 应改写为 `C1`–`C8`，避免与 orbit 的 `K1`–`K9` 混淆。这是合并前必须做的一处迁移。

### 2.3 总知识库 `shared` 装什么

只装**真正跨模块共用**的内容，避免变成什么都往里塞的杂物间。判据是：**这条知识是否会被两个以上模块引用？**

| 类别 | 内容示例 | 会被谁引用 |
|---|---|---|
| 对称性与群论基础 | 对称操作类型、点群记号、群的基本概念 | crystal、symmetry |
| 量子力学基础 | 波函数、概率诠释、量子数 | orbit、crystal（成键部分） |
| 化学键理论 | 离子键/共价键/金属键/范德华力/氢键 | crystal、orbit |
| 结构—性能关联总纲 | 同素异形体、结构与性质的关系 | crystal、orbit |
| **跨模块概念映射** | 同一概念在各模块中的呈现方式 | 全部 |

**跨模块概念映射**是总库独有的价值，举两例：

| 概念 | orbit 里怎么讲 | crystal 里怎么讲 | symmetry 里怎么讲 |
|---|---|---|---|
| 对称性 | 轨道的轴对称（复函数） | 晶体点阵与空间群 | 分子点群与对称元素 |
| 简并 | n 层内 l 不同能量相同 | 等效点系 | 不可约表示维数 |

有了这张映射表，统一智能体在回答"为什么 3d 有 5 个轨道"和"为什么立方晶系有 3 个轴"时，能主动把两处讲法串起来——**这是三个独立模块各自做不到的**，也是合并的价值所在。

## 三、决策节点约束层（本设计的核心）

### 3.1 为什么要做节点约束

因为**同一个模型在不同任务上应该有不同的权限与纪律**。目前（orbit 现状）所有节点共用一套系统提示，模型在出题时理论上可以操控视图、在讲解时可能越界出题、在诊断时可能直接把答案说出来。

靠提示词里写"请不要…"是软约束，模型可能不遵守。**本设计改用硬约束**。

### 3.2 核心机制：工具白名单

> **每个决策节点的能力边界，由它能调用哪些工具来定义。**

这是结构性的，不依赖模型自觉：出题节点拿不到操控视图的工具，它就**做不到**在出题时乱动画面——不是"不应该"，是"不能"。

工具按能力分为四类：

| 类别 | 工具 | 说明 |
|---|---|---|
| **读** | `getSnapshot`、`getInteractionTrace`、`getLearningProfile` | 感知，无副作用 |
| **查** | `queryCrystal`、`loadKnowledge`、`loadSkill`、`searchKnowledge` | 取事实，无副作用 |
| **手** | `applySceneActions`、`highlightAtoms`、`startDemoSequence` | **有副作用**，会改变视图 |
| **教** | `generateQuiz`、`checkAnswer`、`diagnoseError`、`evaluateExplanation`、`recordLearningEvent` | 教学流程 |

读与查是安全的，任何节点都能用。**手与教需要按节点授权**。

### 3.3 八个决策节点及其约束

#### 节点 1　`route`　意图分流

| 项 | 规格 |
|---|---|
| **职责** | 判断用户想做什么，转给对应节点。自己**不产生教学内容** |
| **工具白名单** | 读类 + `loadKnowledge`（仅用于消歧） |
| **输入** | 用户原话 + 感知快照 |
| **输出契约** | 只输出 `{intent, confidence, slots}`，不输出讲解文字 |
| **硬性禁令** | ① 不得操控视图；② 不得出题；③ 意图不明确时**必须反问**，禁止猜测（继承小程序版已有的"歧义即澄清"铁律） |
| **降级** | 置信度低于阈值 → 转 `explain` 并附一句澄清提问 |

#### 节点 2　`explain`　知识讲解

| 项 | 规格 |
|---|---|
| **职责** | 讲解知识点，**边讲边把视图调到对应状态** |
| **工具白名单** | 读类 + 查类 + **手类**（完整操控权） |
| **输入** | 知识点 id + 学情画像（决定讲解深度） |
| **输出契约** | 讲解文本 + 动作序列（每步含旁白 `speech`），动作 4–8 个一组 |
| **硬性禁令** | ① **一切数值必须来自 `queryCrystal` 或知识条目，禁止口算**；② 引用知识条目内容时不得改写数值；③ 超纲内容明确说"不在本课程知识库范围内" |
| **降级** | 知识条目缺失 → 用晶体数据的结构化字段组织讲解，并标注"以下为基于结构数据的说明" |

#### 节点 3　`quiz`　出题

| 项 | 规格 |
|---|---|
| **职责** | 生成练习题 |
| **工具白名单** | 读类 + 查类。**★ 不含手类，不含教学类** |
| **输入** | 知识点 id + 晶体 id + 难度层级 |
| **输出契约** | 题干 + 4 选项（每项带错因标签）+ 正确答案 + 知识点归属 + **预置观察状态** `presetView` |
| **硬性禁令** | ① **完全不能操控当前视图**（出题时乱动画面会打断学生思考）；② 数值题必须走确定性生成路径，模型不得参与数值生成；③ 答案与解析**分离生成**（先冻结答案再写解析） |
| **降级** | 确定性生成器不可用 → 只出概念题，且必须通过双源校验 |

> **注意 `presetView` 与手类工具的区别**：出题节点产出的 `presetView` 是一份**数据**（描述"点按钮后视图该是什么样"），不是立即执行的动作。它由前端在学生点击"去看结构"时才应用。这样既实现了"做题时能跳回结构验证"，又不违反"出题不动当前画面"的约束。

#### 节点 4　`grade`　判卷与错因诊断

| 项 | 规格 |
|---|---|
| **职责** | 判定答案正误，归因错因，执行可视化诊断 |
| **工具白名单** | 读类 + 查类 + **手类（仅诊断动作）** + `recordLearningEvent` |
| **输入** | 题目 + 学生答案 |
| **输出契约** | 正误 + 错因类型 + 诊断动作序列 + 引导话术 + **不得包含正确答案的明文**（除最终确认环节） |
| **硬性禁令** | ① **答错时不直接给出答案**，先执行诊断动作引导学生自己看出来；② 不得用"你错了"开头；③ 诊断动作不得超出 `presetView` 所描述的范围 |
| **降级** | 错因无法归类 → 走通用诊断（展示相关结构 + 开放式提问） |

#### 节点 5　`demo`　演示编排

| 项 | 规格 |
|---|---|
| **职责** | 把教学意图编排为分镜序列 |
| **工具白名单** | 读类 + 查类 + **手类（完整操控权）**。不含教学类 |
| **输入** | 自然语言教学意图（如"讲一下 NaCl 为什么是 6 配位"） |
| **输出契约** | 分镜队列，每步含 `action` + `params` + **`speech` 旁白（必填）** |
| **硬性禁令** | ① **每步必须写旁白**——没写旁白的那一步，学生只会看到画面莫名跳了一下；② 旁白不得写成"点击下一步继续"这类操作指令（按钮本身已说明）；③ 单次 4–8 步，长流程分次下发 |
| **降级** | 意图无法编排 → 降级为 `explain` |

#### 节点 6　`teach`　教学法执行

| 项 | 规格 |
|---|---|
| **职责** | 按选定的教学法技能（费曼/苏格拉底/类比…）推进对话 |
| **工具白名单** | 读类 + 查类 + 手类（辅助演示）+ `evaluateExplanation` |
| **输入** | 技能名（由 `route` 选定或用户指定）+ 知识点 |
| **输出契约** | 必须先 `loadSkill(name)` 取完整步骤，再按 `steps` 推进；受 `when`/`exit`/`cautions` 约束 |
| **硬性禁令** | ① **未加载技能不得凭印象执行**；② 苏格拉底追问**不超过 3 轮**；③ 学生明显挫败时**必须**切换为讲解模式；④ 类比教学**必须**附"类比失效边界"说明 |
| **降级** | 技能未注册 → 回退为 `explain` |

#### 节点 7　`proactive`　主动介入

| 项 | 规格 |
|---|---|
| **职责** | 依据行为数据主动提出帮助 |
| **工具白名单** | 读类 + 查类。**不含手类**——主动提示**只提议、不执行** |
| **输入** | **行为数据**（停留时长、图层切换次数、模型切换次数、点击历史），非对话内容 |
| **输出契约** | 一条提示文本 + **建议动作**（作为候选项呈现，由用户点击才执行） |
| **硬性禁令** | ① **不得直接执行动作**；② 同一规则 3 分钟内不重复（冷却）；③ 两次主动提示至少间隔 45 秒；④ 用户可全局关闭 |
| **降级** | 本地规则未命中 → **完全静默，不唤起模型**（这样主动服务在未命中时零 token 成本） |

> 节点 7 是唯一一个**本地规则先筛、命中才唤起模型**的节点。orbit 的实现是每 2.5 秒检查一次本地规则，不花 token。

#### 节点 8　`compare`　结构对比

| 项 | 规格 |
|---|---|
| **职责** | 对比两个晶体的结构差异 |
| **工具白名单** | 读类 + 查类 + 手类（跳转对比页）+ `queryCrystal(kind='compare')` |
| **输入** | 两个晶体 id |
| **输出契约** | 对比维度表（同分类？同晶系？同点阵型式？）+ 差异点列表 + 并排视图 |
| **硬性禁令** | ① **两个 crystalId 必须来自上游工具返回的原值，禁止编造或从自然语言推断**（继承小程序版已有铁律）；② 对比结论必须基于结构化字段，不得主观评价 |
| **降级** | 任一 crystalId 缺失 → 先调 `searchCrystals` 补全 |

### 3.4 节点约束的汇总表

| 节点 | 读 | 查 | 手 | 教 | 最关键的禁令 |
|---|:--:|:--:|:--:|:--:|---|
| `route` | ✓ | ✓ | ✗ | ✗ | 歧义必须反问，禁止猜测 |
| `explain` | ✓ | ✓ | ✓ | ✗ | 数值禁止口算 |
| `quiz` | ✓ | ✓ | **✗** | ✗ | 不得操控视图；答案解析分离生成 |
| `grade` | ✓ | ✓ | 仅诊断 | ✓ | 不得直接给答案 |
| `demo` | ✓ | ✓ | ✓ | ✗ | 每步必须写旁白 |
| `teach` | ✓ | ✓ | ✓ | 部分 | 未加载技能不得执行；追问 ≤3 轮 |
| `proactive` | ✓ | ✓ | **✗** | ✗ | 只提议不执行；未命中零成本 |
| `compare` | ✓ | ✓ | ✓ | ✗ | crystalId 禁止编造 |

### 3.5 实现方式

在 orbit 的 `_nodePrompt` 钩子基础上，把节点约束做成一份**可声明的规格表**：

- 每个节点声明：`{ name, systemPrompt, allowedTools, forbidden, fallback }`
- `agent-core` 每轮按当前节点组装系统提示，并**只把 `allowedTools` 里的工具注册进本次 function-calling 列表**
- 工具白名单在**工具注册阶段**生效，而非靠提示词劝说——模型看不到不允许的工具，自然也调不到

这一点的价值：**约束从"提示词的礼貌请求"变成"系统能力边界"**。前者模型可能不遵守，后者结构上无法违反。

### 4.2 条目示例（示范格式与深度）

```
id:            crystal:C4-2
kp:            crystal:C4
title:         CsCl 型为什么是 6:6 之外的 8:8 配位
keywords:      [CsCl, 配位数, 8配位, 体心, 简单立方]
source:        [周] 结构化学基础 · 离子晶体章节
body:
  CsCl 型结构中，每个 Cs⁺ 被 8 个 Cl⁻ 包围，每个 Cl⁻ 也被 8 个 Cs⁺ 包围，
  配位数之比为 8:8。8 个 Cl⁻ 位于立方体的 8 个顶点，Cs⁺ 位于立方体中心，
  构成**立方体配位**。

  ★ 关键辨析：CsCl 型常被误称为"体心立方结构"，但其**点阵型式是简单立方(cP)**：
  Cs⁺ 与 Cl⁻ 是不同种离子，体心位置与顶点位置的内容不同，
  不能构成体心点阵。其结构基元含 2 个原子（1 个 Cs⁺ + 1 个 Cl⁻）。

  配位数 8:8 的成因是离子半径比 r₊/r₋ 较大（约 0.73 以上），
  阳离子较大，需要更多阴离子才能包围。

misconceptions:
  - 把 CsCl 型称作"体心立方结构"（点阵型式应为简单立方 cP）
  - 把配位数记成 6（与 NaCl 混淆）
  - 认为 Cs⁺ 在体心就说明是体心点阵（混淆了"位置"与"点阵型式"）
  - 把结构基元写成 "CsCl₂" 或漏掉 Cl⁻
```

**注意 `misconceptions` 里第 1 条**：这正是本项目数据核查中真实发现的问题——CsCl 的 `latticeType` 原本就写作“体心立方(cI)”，与空间群 `Pm-3m` 矛盾。**知识库条目的编写过程本身就会暴露数据集里的问题**，这是编写知识库带来的一项额外收益。

### 5.2 模块专属技能设计

**① `layer-progression`　分层递进讲解**

这是**论文里已明确描述的教学法**——"由整体到局部、由几何构型到晶体学信息逐层呈现"，是"晶典在线"图层控制功能的教学价值所在。

| 项 | 内容 |
|---|---|
| `when` | 学生首次接触某个晶体；或表示"看不明白""太乱了"时 |
| `steps` | ① 只留原子与晶胞线框，建立整体印象 → ② 打开坐标轴，明确取向 → ③ 打开点阵点，识别点阵型式 → ④ 打开化学键，看连接关系 → ⑤ 按需打开空隙/对称元素 → ⑥ 反向拆解，回到最简 |
| `exit` | 学生能自主说出"这个结构的点阵型式是…配位数是…" |
| `cautions` | 一次只加一个图层；**不要一开始就把所有图层打开**（这是学生"看不懂"的常见成因） |

**② `structure-comparison`　结构对比**

利用工具已有的双模型对比页。

| 项 | 内容 |
|---|---|
| `when` | 学生混淆两个结构时（如 NaCl 与 CsCl、金刚石与石墨、A1 与 A3） |
| `steps` | ① 先让学生分别说出两个结构各自的要点 → ② 并排展示 → ③ 引导找出**差异维度**（点阵型式？配位数？堆积方式？）→ ④ 逐个维度对比 → ⑤ 回到单个结构确认 |
| `exit` | 学生能说出至少 3 个维度的差异 |
| `cautions` | 先对比再总结；不要先给结论再让学生"验证" |

**③ `packing-derivation`　堆积推演**

从最密堆积出发，推导空隙与配位数——这是结构化学的核心推理链。

| 项 | 内容 |
|---|---|
| `when` | 讲 A1/A3 堆积、空隙分布、配位数时 |
| `steps` | ① 先用 CPK 模型建立"球贴球"的图像 → ② 打开面对角线，展示密堆积方向 → ③ 打开空隙图层，数出空隙 → ④ 由空隙推出可容纳的离子数与配位比 → ⑤ 回到实际晶体验证 |
| `exit` | 学生能独立推出"每个球周围 6 个八面体空隙、8 个四面体空隙" |
| `cautions` | 严格区分**晶胞内空隙总数**与**每个球周围的空隙数**（这是本项目中真实存在的数据陷阱，两者数值不同） |

**④ `notation-reading`　晶体学记号识读**

| 项 | 内容 |
|---|---|
| `when` | 学生问到点阵记号 "cF"、空间群符号 "Fm-3m"、"4b 位"等记号的读法 |
| `steps` | ① 拆解记号的构成（晶系字母 + 点阵字母）→ ② 对照当前晶体验证 → ③ 举反例（如 CsCl 是 cP 不是 cI）→ ④ 让学生自己读一个新记号 |
| `exit` | 学生能独立读出并解释一个没见过的点阵记号 |
| `cautions` | 记号的字母含义必须准确；不要为了简化而省略"P 表示简单点阵"这类关键信息 |

## 六、与 orbit / Symmetry Viewer 的合并路径

### 6.1 三个模块的知识边界

| 模块 | 核心知识 | 与另两个的交集 |
|---|---|---|
| **orbit** | 原子轨道、波函数、量子数、节面、相位、杂化 | 与 crystal：成键与堆积的量子力学基础<br>与 symmetry：轨道的对称性 |
| **crystal**（本项目） | 点阵、堆积、空隙、配位、空间群 | 与 orbit：原子半径、成键<br>与 symmetry：空间群、对称元素 |
| **symmetry** | 点群、对称操作、特征标 | 与 crystal：空间群<br>与 orbit：轨道对称性 |

**交集集中在一个概念上：对称性。** 这决定了总知识库应优先建设对称性部分。

### 6.2 合并时的迁移清单

| 迁移项 | 动作 |
|---|---|
| 知识 id | orbit 的 `K1-1` → `orbit:K1-1`；crystal 的 `K1-1` → `crystal:C1-1` |
| 技能 id | 通用的移入 `common/`；专属的加模块前缀 |
| 节点约束 | 通用节点（route/teach/proactive）抽到共享层；模块专属节点（quiz/compare）留在模块内 |
| 工具注册 | 各模块自注册，统一命名空间前缀（如 `crystal.searchCrystals`） |
| 系统提示 | 由「基础契约 + 当前模块契约 + 节点约束」三段拼装，模块契约按当前所在模块切换 |
| 跨模块推荐 | orbit 已在系统提示里做了一件事：遇到晶体堆积、分子对称性的问题建议改用其他模块。合并后应改为**直接路由**，而非建议用户切换 |

### 6.3 现在就要做的准备（避免将来返工）

1. **知识点编号改 K → C**（见 §2.2）——这是硬性前置，越早改越好
2. **id 一律写全命名空间**，即便现在只有一个模块
3. **节点约束按可声明规格表设计**，而非硬编码在提示词字符串里
4. **通用技能与专属技能分目录存放**，从一开始就分开
5. **跨模块推荐走统一的 `route` 节点**，为将来直接路由留出接口
