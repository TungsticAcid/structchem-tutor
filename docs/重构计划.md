# chem-agent 重构计划

## Context（为什么做这件事）

本仓库由三个独立项目于 2026-09-24 复制合并而成，目标是**一个智能体 + N 个可插拔教学模块**。合并只做了文件级拷贝，没有做结构整合，于是「乱」表现出来是同一件东西存了多份：

**仓库**：`https://github.com/TungsticAcid/structchem-tutor`（2026-09-24 新建）。三个子项目的 `LICENSE` 均为同一份 MIT（`Copyright (c) 2026 TungsticAcid`），与仓库属主一致——**合并无第三方版权问题**。

| 重复形态 | 数量 | 证据（已实测） |
|---|---|---|
| 三个独立前端入口 | 3 套构建方式 | orbit 无构建（28 个 `<script>` + `window.*`）；crystal / symmetry 是 Vite + ESM |
| three.js | **3 个版本** | orbit r147（vendored UMD）/ crystal 0.170 / symmetry 0.160 |
| 晶体数据 | 3 份 JS + **1 份未登记的上游 CIF** | 23/23 正文逐字节相同，仅第 1 行模块语法不同；`miniprogram/cod_data/` 24 个 CIF 才是真上游 |
| symmetry 引擎 | **2 份（16 个文件 100% 字节相同）** | 全仓最大的一块重复 |
| 元素表 | **5 份** | crystal ×3 + symmetry ×2；且 crystal 与 symmetry 之间 94.5% 相似、**有 8 行差异** |
| 智能体 | **只有 orbit 有** | 18 文件 5642 行，长在 `projects/orbit/H5/js/agent/`，另两个模块用不上 |
| 跨项目手写重复 | 1 个文件 | `touch-handler.js` 三份字节全同（md5 相同） |
| `.gitignore` | 5 份，两两相似度仅 24–38% | 各自演化 |
| 同名不同文 | 2 组 | `AI智能体建设方案.md` 在 crystal 与 orbit 各一份，**句子重合度 0.0%** |

## 目标架构（核心蓝图）

### 五个层次

```
┌──────────────────────────────────────────────────────────────┐
│ L1  总智能体（化学教学智能体）                                  │
│     路由（route 节点）· 总知识库 shared · 总技能库 common        │
│     跨模块联动（仅在 explain/compare 节点开放）                   │
├──────────────────────────────────────────────────────────────┤
│ L2  模块智能体 ×3（晶体 / 轨道 / 对称）＝ 你说的「小智能体」          │
│     人格提示 + 模块知识库 + 模块技能库 + 模块工具集 + 能力声明     │
│     ← 由 registry/descriptors/*.js 声明，可插拔                  │
├──────────────────────────────────────────────────────────────┤
│ L3  决策节点约束  nodes/constraints.js        ✅ 已有            │
│     8 个节点的工具白名单 —— 权限不写在提示词里                    │
├──────────────────────────────────────────────────────────────┤
│ L4  智能体运行时  packages/agent-core/{core,ui}                 │
│     ⬅ 从 orbit 上移：对话循环 · LLM 客户端 · 分镜队列 ·           │
│        感知快照 · 面板与流式渲染                                 │
├──────────────────────────────────────────────────────────────┤
│ L5  共享表现层  packages/ui-kit（设计令牌·构件）                 │
│                packages/viewer（three 外壳·相机·场景原语）        │
├──────────────────────────────────────────────────────────────┤
│ L6  模块实现  modules/<id>/：数据 · 视图 · 动作词汇表 · 设置表    │
└──────────────────────────────────────────────────────────────┘
```

只有一个运行时（L4），一个 AI 面板，一个入口。三个模块不是三个独立应用，而是**同一智能体下的三种可插拔能力**。

### 三条贯穿全局的设计原则（都已在现有代码里有成型范例，不是新发明）

| 原则 | 已有范例（可直接照搬） | 在目标架构中的推广 |
|---|---|---|
| **约束靠白名单，不靠提示词** | `nodes/constraints.js` 的 8 节点工具权限 | 跨模块工具的可见性同样按节点裁决（见 B6b） |
| **数值一律程序算** | orbit `observables.js` 全部解析式，注释明说「从结构上杜绝幻觉」 | `applyModuleSettings` 的取值域夹紧；晶体数值题由程序从数据计算 |
| **渐进式披露** | `knowledge.js` 的 `index()`/`load()` 两段式；`tool-registry.js` 的两层工具 | 动作词汇表、参数字典、模块知识索引全部按需加载 |

### 知识库与技能库的分层（回应你的问题）

**你的方案合理，而且它就是现有设计**（`packages/knowledge/{shared,crystal,orbit,symmetry}/`、`packages/skills/{common,<module>}/`）。理由是它与上述两条原则是同一个思想的第三次应用——**不给模型看它此刻不需要的东西**：模型注意力的边界，就是可见性的边界。

| 层 | 内容 | 加载时机 |
|---|---|---|
| 模块清单 | 三个模块的 `id`/`title`/`capabilities` | 启动时常驻（体量极小） |
| 模块知识索引 | `{id, kp, title, keywords}` | **route 确定模块之后**才加载 |
| 条目 body / misconceptions | 正文与常见误解 | 模型主动 `loadKnowledge(id)` 时 |
| 模块专属技能 | 学科教学法 | 随模块加载 |
| 总知识库 `shared` | 跨模块共用 | 按类目，见下 |
| 通用技能 `common`（6 个） | 学科无关教学法 | 常驻索引（仅 139 行） |

**三条必须补上的约束，否则会退化：**

1. **`shared` 必须有严格准入判据**，否则会变成杂物间。判据已写在 `智能体知识资产设计.md` §2.3：**「这条知识是否会被两个以上模块引用？」** 过不了这条线的不进 `shared`。`shared` 内部也只有「跨模块概念映射」总纲适合常驻（体量小、价值密度高），其余按类目按需。
2. **模块知识索引不得在启动时全量加载**——那等于三个模块的索引都常驻，分层就白做了。必须在 `route` 节点确定模块之后加载。
3. **跨模块引用要留一个显式出口**，否则「只让当前模块可见」会挡住必要的联动（讲晶体配位时要引用轨道对称性）。出口是：在 `explain`/`compare` 节点显式开放 `shared` + 指定关联模块的 `query`，**而不是放宽全局**。

> 技能库与知识库的分层策略**略有不同**，不要混为一谈：6 个通用教学法**学科无关**（`skills/index.js:139` 行全无学科词），且靠自身的 `when`/`exit` 条件决定何时启用，因此索引可以常驻；知识条目的 `body` 才是真正需要按需加载的重内容。

#### 相机层：三个实现分属两种范式（统一 3D 外壳的核心决策）

「三个项目都是四元数控制器」**前半对、后半需修正**——都用四元数，但**拖拽时被旋转的对象不同**：

| | orbit | crystal | symmetry |
|---|---|---|---|
| 姿态表示 | ✅ `THREE.Quaternion` | ✅ 四元数 | ✅ 四元数 |
| **拖拽改的是谁** | **相机** `camera.quaternion` | **模型** `crystalRoot.quaternion` | **模型** `root.quaternion` |
| 范式 | 相机轨道 + trackball（转观察者） | 固定相机 + 模型 arcball（转世界） | 同 crystal |
| 投影 | `PerspectiveCamera` | `OrthographicCamera` | `OrthographicCamera` |
| 输入抽象 | **Pointer Events 单套**（含 `pointercancel` + `setPointerCapture`）→ 支持触控笔 | `touch*` + `mouse*` 两套 → 不支持触控笔 | 同 crystal |
| 阻尼 | ✅ `slerp` | ✗ 完全跟手 | ✗ |
| 滚轮 | ✅ 连续映射 `exp(deltaY·k)` | ✗ `deltaY>0?1.1:0.9`（忽略幅值） | ✗ 同 crystal |
| 平移换算 | ✅ 几何精确 `2·d·tan(fov/2)/h` | ✗ 裸系数 `0.02` | ✗ 裸系数 |
| best-view 对齐 | ✗ | `setView` 四方向 | ✅ `alignToView(dir)` |
| 与宿主耦合 | **无**（签名 `(camera, dom, opts)`，同项目内已实例化两次验证：fov 50 / 45） | 强耦合（要求宿主有 `crystalRoot`，旋转后还须调 `updateWorldClipPlanes`） | 强耦合（同理） |

**结论：以 orbit 的 `createQuatOrbit`（`render3d.js:43-204`）为 `packages/viewer` 相机层骨架。**

**但不强行统一交互语义**——「转相机」与「转模型」各有教学用途（晶体有晶体学轴对称，转模型会丢失「沿 a 轴看」的参照）。正确做法是**共用输入层与数学，把「四元数写进哪一帧」参数化**：

- 共享：输入抽象（Pointer Events 统一鼠标/触摸/笔）、pinch/roll 语义、阻尼、`worldPerPixel()` 平移换算、连续滚轮、`pointercancel`/`touchcancel` 复位
- 差异：`mode: 'camera'`（orbit）vs `mode: 'object'`（crystal/symmetry）——**只差把结果四元数写进 camera 还是写进 root**

**正交与透视可共用同一控制器**，只需抽象两个口子（已验证唯一的硬阻断点是一行 `render3d.js:111` 用了 `camera.fov`，正交下为 `undefined` → 平移系数变 `NaN`）：

| 口子 | 透视 | 正交 |
|---|---|---|
| `worldPerPixel()` | `2·distance·tan(fov/2)/h` | `frustumSize/h` |
| `zoomBy(factor)` | 改 `distance` | 改 `frustumSize` |

### B6b. 跨模块联动与「两层工具 + 渐进式披露」（你 2026-09-24 追加）

**要求**：总智能体能调用**多个模块**的工具（跨模块联动），且能触达**细粒度设置与小参数**（动画速度、标签字号、原子缩放、元素颜色、背景色、对称元素大小等），**但不能让这些参数撑爆常驻上下文**——必须遵守渐进式披露。

> 术语说明：此处「小程序」理解为**三个教学工具模块**（晶体/轨道/对称），不是微信小程序（后者已按你的指示删除）。

**解法已在 orbit 里成型，只需泛化**——`tool-registry.js` 的**两层工具设计**（`1-13` 行注释）：

| 层 | 内容 | 是否常驻上下文 |
|---|---|---|
| 第一层 | 语义工具：`getSnapshot` / `query*` / `applySceneActions` / `loadKnowledge` / `generateQuestion` / `diagnoseError` / `recommendNext` 等 | ✅ 常驻（约 14 个） |
| 第二层 | 动作词汇表 + 模块设置参数表，**模型按需用 `listSceneActions` 类工具拉取** | ❌ 不进常驻上下文 |

**token 效率的关键正在第二层**：动作与参数表可能上百项，全塞进系统提示是灾难；靠按需拉取，模型需要时才读。同一机制直接复用于**「小设置小参数」**——新增一个 `listModuleSettings(moduleId)` 类工具返回参数索引（名称/类型/取值域/默认值），真正改值时走 `applyModuleSettings`。

**跨模块联动的三条设计约束**：

1. **工具名一律带模块前缀**（`crystal.searchCrystals`、`orbit.applySceneActions`），但**白名单仍按「类别」裁决**——`nodes/constraints.js` 的工具类别（read/query/hand/teach）不变，避免每加一个模块就要改权限表
2. **跨模块调用是能力，不是默认**：`route` 节点决定当前模块后，其余模块的工具**不应默认可见**（否则模型会答非所问地跨模块乱调）。仅在 `explain`/`compare` 这类确实需要联动的节点上开放跨模块 `query`
3. **参数取值域由程序校验，不由提示词约束**（CLAUDE.md §一.2）：`applyModuleSettings` 的 schema 必须声明取值范围并做夹紧，模型无法把动画速度设成负数

这与 `智能体知识资产设计.md` §2.3 的「跨模块概念映射」表是同一思路的两个层面：那边解决**讲法联动**（同一个概念在三个模块里怎么讲），这边解决**动作联动**（一个模块的板书能不能由另一个模块渲染）。

## 与计划的偏差（已按实际调整，原因逐条写明）

1. **B6b「工具名一律带模块前缀」→ 改为「中枢工具不带前缀 + 模块专属工具仅在激活时可见」**。
   原因：OpenAI 的 function name 只允许 [a-zA-Z0-9_-]，点号不合法；而下划线前缀既丑又对模型不友好。
   **可见性隔离比名字前缀更能达到同一目的**（防止跨模块误调）。

2. **getSnapshot / listSceneActions / applySceneActions 从模块上移到中枢**。
   原因：三者语义与模块无关；各模块各实现一遍会造成命名冲突，更要命的是**行为分叉**
   ——模块版容易只做校验而忘了入队，于是「动作立刻执行、没有分镜队列」。
   连带把 CORE_TOOLS 从「只列 loadKnowledge/loadSkill」扩为 5 个中枢工具。

3. **物理去重推迟到 B6 之后**。元素表、orbit 条目、symmetry 特征标表都先建「真源 + 守卫」
   （逐字段比对，防漂移），物理上的 import 改指留到模块收编时做——
   立即改指会让原项目的 Vite dev server 遇到跨根目录导入限制。

4. **修 check-crystal-data.mjs 提前到 A0**（原计划在 B7）。因为它守护后续所有数据改动，
   而它在合并后**从任何目录都跑不起来**。
